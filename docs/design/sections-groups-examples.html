Sections and groups, worked through

A proposed model for part B of the drag model: user-curated sections and groups as Andamento entities, nested by facts, the way part A put a local workspace in a project. Pick a scenario to see what is saved, what Andamento receives, and what the sidebar shows.

.sectionA section you made. Placed by a layout="section" loop, so each is its own docked sidebar View. Facts: display.label.
.groupA group inside a section. Facts: display.label, .section (which section), .refs (its ghosts, in order).
.workspaceA host's local workspace (part A's wheelhouse.workspace, renamed). Lives in a group via .group, or with a project via flotilla.project.

KDL that places all of this (once, in the shipped config)

// One region holds every section you made. A loop with layout="section"
// makes each iteration its own section; docking frontends give each one a View.
region "local" root-template=".local/title" placement="local"

placement "local" {
  for "section" kind=".section" layout="section" {
    apply-template ".section/line"
  }
}
template ".section/line" {
  field "label" key="display.label"
  // Groups name their section, as convoys name their project.
  for "group" kind=".group" {
    match ".section" of="section"
    apply-template ".group/line"
  }
}
template ".group/line" {
  field "label" key="display.label"
  // Workspaces that live in the group.
  for "workspace" kind=".workspace" {
    match ".group" of="group"
    apply-template "wheelhouse/entry"
  }
  // Ghosts: the referenced entities themselves, in the group's order.
  for "ghost" in=".refs" of="group" {
    apply-template "wheelhouse/entry"
  }
}

Two things here are new in Andamento: the layout="section" loop intent (each iteration is its own section; the terminal renderer shows it as a headed section, Wheelhouse gives it its own docked View), and a ghost being placed through a reference list. Roles already use in= … of=, so the second may mostly exist. Names starting with . are Andamento's own system kinds and facts; conventions producers share, such as display.label and flotilla.project, keep theirs.

Still open after these examples

  • Ghost state: each ghost's own id, compact or expanded, and the same entity twice in one group. A plain reference list holds none of that.
  • The default Workspaces group: is it a group with a reserved id, and does Wheelhouse set .group on every unhomed workspace, or does Andamento's leftover coverage stay the default?
  • Who stores it: Wheelhouse's window layout (published, as now), or Andamento itself, so the terminal frontend could curate too.
  • Drop intent: in this model a workspace dropped on a group moves there, and anything else becomes a ghost. Is that enough, or does a workspace sometimes want a ghost?
