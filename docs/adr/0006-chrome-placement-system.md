# Shell Chrome Is a Placement System, Not Hardcoded Bars

Shell controls — the new-workspace button, the overview toggle, sidebar-collapse, the main menu, the workspace **Tab Strip** — are **Chrome Elements** placed into **Niches** within **Chrome Hosts** (the title bar today; the **Control Surface** and a status bar later), not fixtures wired into a particular bar. A host lays out an ordered sequence of niches; a niche is an anchored flex container holding fixed-size controls and at most one growable element. Niches are either **platform-reserved** — mac window decorations and owner-drawn window controls, whose presence and size the window manager dictates and the shell flows around — or **shell-owned**. The title-bar host reads, left to right, as `[mac-decorations*] [leading buttons] [menu] [center] [trailing buttons] [window-controls*]` (`*` platform-reserved); not all niches are present in every configuration, and the platform pair is present per OS and decoration mode.

Each **Chrome Element** declares a **Placement Chain**: an ordered list of acceptable placements that may span hosts, the first being its default, the last a terminal option (hidden, or an overflow menu). **Placement Resolution** is per-host and *measured* — reserve the platform niches, sum the actual widths of the elements assigned to the host, and while they overflow, move the lowest-priority element to the next link in its chain — which replaces the hand-tuned width breakpoints (the 60em/80em gates) the title bar uses today. The default placement is declared in code and the override lives in config, so chrome layout reuses the same default-in-code / override-in-config model as code-declared settings (ADR-pending tweak/settings work) — no new config machinery, and chrome layout becomes themeable and per-context later for free. Physical space wins over a user override: an element that cannot fit even where pinned is still relocated down its chain rather than clipped (clipping is the failure mode being removed). Termination and the absence of cycles come from two rules: every chain ends in a terminal option, and hosts resolve in a fixed order (title bar, then sidebar), so an element overflowing one host joins the next host's pool before it resolves. An element that must always be reachable (the main menu) has a chain that terminates in a representation, never in hidden.

The menu is one element with three representations selected by platform and an option, not three things: native (mac default — lives in the system menu bar, leaving the in-window menu niche empty), an owner-drawn horizontal bar (the RAD shape, in the menu niche), or a Chrome-style dropdown collapsed to a single button in the trailing niche. uishell's defaults: native menus on mac; the dropdown on Windows/Linux (and available on mac). The project/owner selector is not assumed — a uishell user overwhelmingly has one context bringing all their threads together, so it is an ordinary placeable element, present only if placed.

The hardest case, and the one that proves the model, is **tabs in the title bar**. This is not a special tab mode: it is the **Tab Strip** element placed in the title-bar host. Doing so promotes the topmost docking row to *be* the chrome row — the tab strip's baseline sits on the current title-bar border (browser-style, the active tab flowing down into the content it belongs to), the shared row's height is what is pushed to the window manager as the custom title-bar height, and the decorations and end-zone buttons vertically center in that same row. The only new mechanism the docking system needs is **edge insets**: the title bar's resolved leading- and trailing-zone widths are handed to the docking layout, which insets the top-tabbed strips that touch a window edge. A single top panel is both leftmost and rightmost, so its strip is inset on both ends; a horizontally split top row insets only the edge-touching strips and leaves interior ones full. This is tractable precisely because the insets are the same end-zone widths Placement Resolution computes for any center content — docking only has to accept two edge insets on its topmost row. Tab overflow stays as today (clipped within the inset span; widen the panel to see more); a dropdown for excess tabs is a separable later piece, not a prerequisite.

The alternatives rejected: hardcoding controls into specific bars with per-control width breakpoints (today's shape — every new control re-tunes magic numbers, and relocation like "this button at the bottom of the sidebar instead" is impossible); and a title-bar-only layout system (foreclosed by the requirement that elements relocate across hosts). Building the placement model over hosts from the start costs a little now and makes the title bar, sidebar, and any future status bar one system. What is deferred, not precluded: the responsive overflow menu as a concrete terminal option, per-context/theme placement overrides, and the tab-overflow dropdown — each rides the model rather than reshaping it.

## Implementation in the immediate-mode UI

The one place this could fight the UI is that **Placement Resolution** chooses, per element, *which niche — i.e. which parent box — to build it under*, and in this immediate-mode UI that choice must be made before the element is built. Sizing runs in `ui_layout_root` *after* the whole frame is built (`ui_core.c` — `ui_calc_sizes_*` / `ui_layout_*` passes), so during build only last frame's rects exist; and the constraint solver (`ui_layout_enforce_constraints__in_place`) can only *shrink* over-budget children by strictness — it cannot move a box to a different parent. So inter-niche relocation is a build-time decision the autolayout structurally cannot make for us.

It fits cleanly anyway because element widths are knowable before building. Text widths are computable analytically with `fnt_dim_from_tag_size_string` (`font_cache.h`) — the same measurement `UI_SizeKind_TextContent` resolves to internally (`box->display_fruns.dim.x`); icon buttons are fixed (≈ row height); and the **Tab Strip** is the elastic element that fills the remainder, so it is never a measured competitor. Platform-reserved niche widths are already obtained this way today: `wm_window_native_title_bar_left_padding` is queried before build and reserved as a leading spacer (`shell_core.c`), with the trailing side being owner-drawn window controls or WM-owned. So the shape is a small **pre-build resolution pass** that, per host, computes available width (host width minus platform reservations), measures the assigned shell elements analytically (the elastic tab strip excluded), and while they overflow pops the lowest-priority element to the next link in its **Placement Chain** — yielding an element→niche map. Each host then builds its assigned list normally, and the elastic tab strip fills its niche's remainder; that remainder *is* the edge insets handed to the docking layout. This pass **complements** the autolayout rather than duplicating it: the resolution pass does inter-niche relocation (choose the parent), the existing shrink-solver does intra-niche fitting (e.g. the tab strip yielding to the insets).

Two implementation decisions, recorded with their leans:

- **A single resolution pass at frame start, over all hosts, rather than per-host in build order.** The title bar builds before the sidebar, so an element overflowing title-bar→sidebar could be threaded through a pool the sidebar reads when it builds — but one up-front pass assigning every element to a final niche, after which each host just builds its list, removes the ordering fragility. Lean: single pass.
- **Analytic measurement, with last-frame `fixed_size` only as a fallback.** Analytic widths (font dim for labels, fixed for icons) avoid a one-frame relocation lag and are the same work `TextContent` already does; no element in the current roster needs the last-frame fallback. Resolution is memoizable — re-run only when a host's width or its element set changes.

Caveat: the measurement+resolution step must stay cheap and ideally memoized; and the main menu in its owner-drawn *bar* representation is itself variable-width (a row of menu titles), so in that form it is a measured contributor sized by summing its titles via `fnt_dim`, not elastic — the same mechanism, just applied to a composite element.

## Status & refinements (implemented)

The menu's three representations and the placeable project selector (above) are now built, with refinements that sharpen the original sketch:

- **Tabs-in-title-bar is independent of the menu form — it is not gated at all.** Tabs share the title-bar row with whatever menu is present: native (mac, row is free), the compact kebab (trailing niche, insets the tab strip on the right), or the full owner-drawn bar (leading niche, insets the tab strip on the left). The element widths feed `chrome_leading_px`/`chrome_trailing_px` so the tab strip insets past whichever menu form is shown. Menu-bar style and tabs-in-title-bar are thus fully orthogonal settings — the earlier "free row" precondition was unnecessary. (Top-level menu titles may later want a slightly distinct colour to read as menu vs. tab; overflow when the bar + tabs are both wide is a future concern.) Both are user settings (`compact_menu_bar`, `tabs_in_title_bar`), default off; `show_project_selector` likewise, default off.
- **The compact menu is the furthest-right shell element** (trailing niche, just inside the OS window controls), matching browser kebab placement; its width feeds `chrome_trailing_px` so the title-bar tab strip insets to clear it.
- **The dropdown is flat (app menus as stacked sections), not nested.** The immediate-mode UI core has a *single* ctx-menu slot (`ui_core.c` — `ctx_menu_key`/`ctx_menu_open`), so a Chrome-style "File ▸" hover-submenu cannot open beside its parent today. The flat sectioned dropdown is the no-new-infra interim. **Nested submenus remain the intended end state**, and the menu *hierarchy* (a tree of menus/items) is orthogonal to its *render host* (in-window floating boxes vs. real OS popup windows): the hierarchy model is built once and the renderer swaps, so investing in a proper hierarchical menu model is not throwaway when menus later move to OS windows. Deferred — ungating tabs (above) made the kebab non-mandatory, so the flat-overflow pressure is off; the full hierarchy is its own slice. (TODO.)
- **Glyph stopgap:** the icon font (`data/icons.ttf`) has no kebab/ellipsis glyph, so the button is drawn as three rounded boxes in the text color. A real glyph (from a bundled font that has U+22EE, or added to the icon font) is the eventual fix.
- **Future:** on mac with the native title bar, the rightmost element wants a small margin for the window's rounded corner. (TODO.)
