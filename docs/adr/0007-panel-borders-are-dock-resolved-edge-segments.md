# Panel Borders Are Dock-Resolved Edge Segments, Not Per-Box Outlines

**Status:** accepted (design grilled 2026-06-16). **Frame pass built 2026-06-16** (branch `dock-frame-spacing`): thin segment borders + flush default + panel focus-accent retired. The **integrated active tab** (partial-edge suppression) is the next chunk.

**As built:** panels stop using `UI_BoxFlag_DrawBorder`; the dock draws each panel's frame as thin filled-rect segments around `content_rect`. Dedup without adjacency bookkeeping: **draw TOP/RIGHT/BOTTOM, never LEFT** (a neighbour's RIGHT, or the window edge), and **skip any side on the workspace boundary** — so interior vertical seams draw once, horizontal seams don't double (the lower panel's tab strip occupies the seam), and the window edge has no border. TOP is the tab/content separator. Segments are built after the inactive-dim scrim (so frames dim with their panel) and before `panel_box` (so they draw in front of content). Panel focus-accent retired via always-`DisableFocusBorder`; the **selected-tab** accent stays until the integrated tab replaces it structurally. Knobs: `panel_gap` (em, default 0 = flush) and `panel_border_px` (px, default 1). The skip-LEFT/TOP rule is tuned for top-tabbed panels; bottom-tabbed horizontal seams may need refinement.

Today every **Panel** (and its active tab) draws its own complete 1px rectangle outline via `UI_BoxFlag_DrawBorder` (`shell_core.c:~7772`), and spacing is a scatter of ad-hoc constants: each panel self-insets `~0.15em` (`:3636`), the window inset is `window_edge_px ≈ 3.4px` (`:5039`), and the **Controlled Split** boundary is a separate `+1px` (`:2873`). Consequences: adjacent panels show *two* parallel borders with a gap; there is no way to express a single shared seam or "no border against the window"; and — decisively — a box outline **cannot** draw the integrated (Chrome-style) active tab, whose defining feature is suppressing the border only along the *active tab's run* (a partial segment of one edge).

**Decision:** the dock becomes the **single owner** of Panel/Region frame borders. After layout it resolves the set of frame edges and draws the survivors as **edge segments** — thin filled rects for straight runs, `R_Rect2DInst` per-corner radii for rounded corners — at a configured thickness, replacing per-box `DrawBorder` for panels and tabs. Because the dock visits each boundary exactly once, "is this edge already handled by a neighbour or the window?" stops being a heuristic and becomes **structural single-ownership** — the worry about detecting already-handled borders dissolves. The normal panel-split tree and the (currently limited) **Controlled Split** both feed the same resolution; transient drag affordances (drop sites `:3303`, split/control boundaries `:3499`/`:2888`) stay separate and untouched.

This makes the whole range expressible as parameters: **gap 0** → one shared seam; **gap > 0** → two bordered cards with space (today's look); **window-edge border** on/off; and the **integrated active tab** as partial-edge suppression yielding one continuous frame around tab+body, with inactive tabs keeping the body border beside them. The border itself never disappears (thickness ≥ 1px); the gap is what forces two lines, so it is "0 or a real value, never a tiny ugly in-between." **Default: flush** (gap 0, single seam, no window-edge border, small tunable window padding); the card look is one setting away.

**No shader change.** `R_Rect2DInst` already carries per-corner radii, `border_thickness`, and `edge_softness`, and is implemented in every backend — segments are thin filled rects and tab corners are per-corner-radii rects, all existing capability. The *only* thing that would need new SDF/shader work is Chrome's concave reverse-curve fillet where the tab flares into the body; that is optional polish, deferred, and would ride the single-source effects toolchain (ROADMAP #19), not four hand-written shaders.

**Considered and rejected:** keep per-box outlines and fake the two hard cases — an overlap-and-fill "patch" rect to erase the active-tab seam segment, plus asymmetric self-insets for shared seams. Rejected because the patch is fragile overdraw and still cannot draw a true single shared seam, and neighbour-aware self-insets re-introduce exactly the "already handled" coordination that single-ownership removes.

**Consequences:**
- A future reader will see panels deliberately do **not** use `UI_BoxFlag_DrawBorder` — the dock draws their frames; that is the point of this ADR.
- The segment pass must emit rounded corners / joins, not just straight lines.
- Border thickness, gap, and window-edge are **user settings** now (ranged → sliders, per the code-declared settings system), migrating to **Theme** metrics later (`docs/theme-design-notes.md` thread B).
- **Integration stays intra-panel:** an active tab opens only into its own body; inter-panel seams stay bordered (a tab never flows into a neighbour). Because `tab_side` is per-panel, tab strips can meet at a seam, and flush removes the `0.15em` self-inset that currently separates them — tab-bearing seams may need a retained minimum separation. Try-and-correct on sight; see the design note.
- **The frame is a per-panel heuristic, not full region resolution (built 2026-06-16).** Each panel borders its *own* seam edges: at flush, `panel_rect` RIGHT/BOTTOM dividers (single-owned via skip-LEFT/TOP, window edges omitted, full-height so a seam spans the tab strip) plus the tab/content line off `content_rect`; at a gap, a `content_rect` body card with the tab strip unboxed above (the tab strip integrates with the chrome, not the panel card). This correctly borders content│content and content│tab-bar edges and removes the window edge, but the full-height divider also borders **tab-bar│tab-bar** adjacencies at flush (two top-tabbed panels side by side; a bottom-tabbed panel above a top-tabbed one) — a minor cosmetic. The *proper* model is a **per-seam region analysis** — enumerate boundary segments, know what's content vs tab-strip on each side, border where ≥1 side is content, and **merge** adjacent tab-strip regions (a graph-colour / region-merge). Deferred as diminishing-returns; it pairs naturally with theme work that visually distinguishes tab-strip vs body (which makes the regions clearer). (Robert, 2026-06-16.)
- **Frame integration is semantic before it is a renderer primitive.** The region/frame resolver should own which selection handles integrate with which frame-bearing regions; the immediate backend may still emit filled edge segments and rounded rects. Richer output — merged SDF regions, continuous material textures, interior curved corners — remains a future rendering direction, not a prerequisite for the current frame ownership model.
